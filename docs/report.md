## 운비서 하루 사용 횟수 제한 — A(말 해석 횟수) `[~]`

보리 요청(2026-11-03, "응 작성해"). 근거: 로드맵 24번 "하루 사용 횟수 제한(요금 튀는 것 막기, 서버 표 필요) — 출시 직전 여기서"(roadmap 222·223줄), sot §4-16 593줄, `unbiseo.md` §8. 11-D(`1e6591f`) 다음, 테스터 모집 전.
둘로 나눔: **A = 말 해석(`unbiseo-parse`) 횟수 + 처리방침**, B = 목소리(`unbiseo-voice`) 횟수. **이번엔 A만.**

### 쉬운 요약
- 운비서에 말을 보낼 때마다 xAI 요금이 나간다. 한 계정이 하루에 쓸 수 있는 횟수를 서버에서 세어 막는다.
- 횟수를 다 쓰면 운비서 카드에 "오늘 운비서를 N번 모두 썼어요. 내일 다시 써 주세요."가 보이고, 다음 날(한국 시각 0시) 다시 쓸 수 있다.
- 숫자는 서버 함수 코드 한 줄이라 나중에 바꾸기 쉽다.

### 현재 상태 (코드 확인)
- `unbiseo-parse/handler.ts`(89줄): 로그인 확인(68줄) → 입력 검사(75줄) → 바로 xAI 부름(78줄). 세는 곳 없음.
- 앱 `unbiseoParse.ts` `messageForStatus`(97~102줄): 401·400·502만 문구, 나머지는 "잠시 뒤 다시 시도해 주세요."
- 되묻기 버튼을 말로 고를 때(24-H-3)는 서버를 안 불러 요금이 없다 — 셀 필요 없음(sot 583줄).
- 서버 표에 사용 횟수를 둘 곳 없음(마지막 DB 변경 `0031`). 사용자별 표는 `references auth.users(id) on delete cascade` 방식(`0019`·`0021`·`0025`) — 탈퇴하면 같이 지워짐.
- 처리방침 2항 81줄: "서버 기록에는 처리 결과·걸린 시간·글자 수만 남습니다" — 회원별 사용 횟수는 새로 남는 기록이라 한 줄 더해야 맞음. 3항 90줄 보유 기간에도 없음. 끝 178줄 "내용이 바뀌면 시행 7일 전부터 서비스 화면으로 알립니다". 시행일 41줄·178줄 2026-11-03. 약관 112줄 "운영자는 운비서 등 일부 기능의 하루 이용 횟수를 정할 수 있습니다"는 이미 있음.
- 공지사항: 마이페이지 > 공지사항(`NoticePage.jsx` 44줄). 글은 코드 안 목록 `NOTICES`(제목·날짜 `2026.08.11` 꼴·본문, 누르면 펼침)이고 지금 0개("등록된 공지사항이 없습니다."). `NoticePage.test.js`는 "공지가 없으면 안내 문구만"을 검사. 새 공지가 왔다는 표시(빨간 점·알림)는 없음 — 열어야 보임.

### 목표 상태 (기대 동작)
1. DB `0032`: 표 `unbiseo_usage`(회원·날짜·종류·횟수, 탈퇴하면 같이 지움). RLS 켬, 본인 줄 읽기만 허용, 앱이 직접 쓰기 불가. 함수 `use_unbiseo(종류, 한도)` 한 번에 "오늘(한국 날짜) 횟수 +1, 한도 넘으면 안 더하고 거절" — 동시에 눌러도 한도를 넘지 않음. 부를 때 그 회원의 8일 지난 줄은 지움.
2. `unbiseo-parse`: 로그인·입력 검사를 통과한 뒤 xAI를 부르기 **전에** 1회 셈. 한도를 넘으면 xAI를 안 부르고 429 + 문구. 세기가 실패하면(서버 오류) xAI를 안 부르고 503 "잠시 뒤 다시".
3. 한도: **하루 20회** `[확인: 2026-11-03 보리 — "20회로하자"]`. xAI가 실패해도 1회로 셈(부르기 전에 세므로).
4. 앱: 429면 "오늘 운비서를 20번 모두 썼어요. 내일 다시 써 주세요." — 홈 카드·떠 있는 운비서 같음. 숫자는 서버 답에 실어 보내 앱과 서버가 어긋나지 않게.
5. 처리방침 개정 `[확인: 2026-11-03 보리 — "처리방침에 그렇게해"]`:
   - 2항 운비서 줄 끝에 "하루 이용 횟수를 지키기 위해 회원 고유 번호·날짜·사용 횟수를 서버에 남깁니다."
   - 3항 1번 끝에 "다만 운비서 사용 횟수는 8일이 지나면 지웁니다."
   - 시행일 41줄·178줄을 **2026년 11월 11일**로. 맨 위(시행일 줄 아래)에 개정 예고 상자: "개정 예고: 2026년 11월 11일부터 운비서 하루 이용 횟수 제한을 위해 회원별 사용 횟수(날짜·횟수, 8일 보관)를 처리합니다(2항·3항)." — 시행일 지나도 그대로 두고, 다음 개정 때 바꿈.
   - 앱 push(예고 게시)가 11-04보다 늦어지면 시행일을 그만큼 미룸(게시일 + 7일).
6. 공지사항 글 1개 `[확인: 2026-11-03 보리 — "공지사항도올리자 20번제한이라고"]` — 앱 push와 함께 올라감:
   - 제목: `운비서 하루 이용 횟수 안내`, 날짜: `2026.11.04`(push 날, 늦어지면 그날로)
   - 본문: `2026년 11월 11일부터 AI 운비서는 계정마다 하루 20번까지 쓸 수 있습니다. 횟수는 매일 밤 12시(한국 시각)에 리셋 됩니다.` `[확인: 2026-11-03 보리 — 문구 고침, 처리방침 문장은 빼라]`
   - 목록 위 주석 `// 실제 공지는 출시 때 추가(임시 글 삭제, 문구 정리 1).` → `// 새 공지는 맨 앞에 추가.`

### 검증
- DB: AGENTS §9 순서 — ① 읽기 질문(이름 겹침·`auth.users` 참조 방식 확인)을 먼저 드림 → ② `0032` 실행 → ③ 사후검증(표 RLS 켜짐·정책 1개·함수 `security definer`·`search_path=public`·`anon` 실행 불가·`authenticated` 실행 가능) + 한도 시험(작은 한도로 두 번 불러 두 번째가 거절).
- 서버 함수: CI `deno check`·`deno test`(새 시험 포함). 배포는 `unbiseo.md` §6 절차(편집기 반영 → 보리 Deploy → 지문 확인 → Verify JWT 꺼짐 확인).
- 앱: `npm test`·타입·빌드(CI). 새 시험은 고치기 전 코드에서 실패하는지 확인(revert-check).
- 실제 확인: 배포 뒤 테스트 계정으로 문장을 보내 정상 답, DB에서 오늘 횟수가 오르는지. 한도 넘김은 SQL로 그 계정 오늘 횟수를 20으로 올려 문구 확인 뒤 되돌림. 배포본 `getdrivelog.com/privacy`에서 예고 상자·시행일 확인.
- 배포 순서: ① SQL(표·함수만 생기고 아직 아무도 안 부름) → ② 앱 push(429 문구 + 처리방침 예고 게시, 11-04까지) → ③ **시행일(11-11)부터** 서버 함수 배포 — 이때부터 횟수를 셈. 앱이 먼저 나가도 서버가 429를 안 보내니 동작은 지금과 같음.
